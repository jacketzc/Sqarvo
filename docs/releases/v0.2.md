# v0.2 发布说明

- 状态：**已完成**（2026-11-04，Linux 验证）。性能基准只覆盖 **debug** 构建；
  Windows / macOS 前端未构建、未验证——见「已知限制」。
- 覆盖里程碑：M3 凭据与 MariaDB（已完成，任务 #20–#25）、
  M6 前端接入与硬化（进行中，Linux 首端接入完成，任务 #26–#29）
- 范围：Linux 前端（GTK4 + libadwaita）+ 本地后端 + MariaDB 驱动。
  本文件由 #29 建立性能基准节，#30 补齐其余小节。

## 概览

v0.2 第一次把后端接上真实界面：Linux 前端可以拉起本地后端、用系统凭据库里的密码连接
MariaDB、在 SQL 工作区执行与取消查询、按每批 500 行拉取并在虚拟化表格里浏览 10 万行结果。
后端新增 `CredentialService`，密码只写操作系统凭据库（Linux Secret Service），连接配置里
只留 `credential_ref`；MariaDB 驱动通过 testkit 的五项不变量，并接入 CI 的服务容器作业。

**它不是完整的数据库客户端**：只有 Linux 有可用界面；SQL 编辑器是纯文本；没有对象树、
事务、数据编辑、导入导出；PostgreSQL 与 Windows/macOS 前端不可用。

## 行为变化

1. **新服务**：proto 新增 `proto/services/v1/credential.proto`，后端多暴露一个
   `CredentialService`（共 6 个域服务）。`MetadataService` / `TransactionService`
   仍返回 `UNIMPLEMENTED`，行为未变。
2. **密码的传递路径**：密码只经 `CredentialService.StoreCredential` 写入系统凭据库，
   `Connect` / `TestConnection` 只带 `credential_ref`，后端在连库前解析（v0.1 没有凭据路径，
   SQLite 不需要密码）。
3. **新错误码**：`credential.not_found`（引用不存在）与既有的 `credential.unavailable`
   （存储不可用）分开；两者都不会退化成空密码握手。
4. **Linux 前端配置文件**：新增 `$XDG_CONFIG_HOME/sqarvo/Sqarvo/connections.json`
   （目录 0700、文件 0600），字段固定为
   `name / driver / host / port / database / username / tls_mode / credential_ref`，
   **没有** password / secret / token 字段。
5. **新环境变量（Linux 前端）**：`SQARVO_RESULT_ROW_LIMIT`、`SQARVO_RESULT_BYTES_LIMIT`
   （结果集上限）、`SQARVO_BACKEND_BIN`（后端路径）、`SQARVO_ENDPOINT_FILE`（端点文件覆盖）。
6. **新错误码（客户端）**：`result.limit_reached` 表示达到**客户端**结果集上限，与服务端的
   `query.limit_reached`（并发查询上限）语义不同，两者不会混用。
7. **内部构建**：后端 `build.rs` 现在监听整个 `proto/` 目录，新增 `.proto` 会自动重新生成；
   对用户无可见变化。

## 已知限制

以下条目都**不可用或未验证**，界面与文档不得把它们呈现为已支持：

1. **Windows / macOS 前端**：`frontend/windows`、`frontend/macos` 只有窗口骨架，未接后端、
   **未构建、未运行验证、未在 CI 覆盖**。v0.2 的「至少一端」由 Linux 满足，不等于跨平台可用。
2. **PostgreSQL 未实现**：未注册驱动，连接与测试连接返回 `driver.not_found`。
3. **事务与元数据未接线**：`TransactionService` / `MetadataService` 返回 `UNIMPLEMENTED`；
   两个驱动的能力描述符都声明 `transactions=false`、无元数据；前端没有对应 UI（M4，v0.3/v0.4）。
4. **SQL 编辑器是纯文本**（`REQ-SQL-001` 未完成）：无语义高亮、无多标签、无行号、无查找替换、
   无查询历史；界面明确标注「当前为纯文本编辑」。
5. **多语句仍未支持**：SQLite 在 prepare 阶段拒绝（rusqlite `MultipleStatement` → `capability.unsupported`），
   MariaDB 在**发送前**用扫描器拒绝（同样 `capability.unsupported`）；契约里的 `statement_index`
   已就绪，但没有任何驱动实现多结果集。
6. **取消的契约缺口**：`ExecuteQueryRequest` 不携带客户端 `query_id`，`query_id` 只在首批
   返回后产生，因此「尚未返回首批」的语句**无法在服务端取消**。界面点击取消后 0 ms 进入
   Cancelled（`frontend/linux` 实测），但服务端可能仍在执行；只能靠 `timeout_millis` 兜底，
   而 Linux 前端目前传 `timeout_millis=0`（由服务端策略决定）。
7. **客户端结果集上限是近似估算**：按「行固定开销 + 每格固定开销 + 显示文本 + tooltip」计算，
   不含 GTK 渲染开销；10 万行估算 25.3 MiB 而 RSS 增量约 42 MB，200 列 2000 行估算 40.0 MiB
   而实际 604 MB。它是防无限增长的护栏，不是 RSS 预测。
8. **宽表内存随列数上升**：200 列 × 2000 行 604 MB，同一轮对照（20 列 × 5000 行 208.6 MB、
   100 列 × 1000 行 376.5 MB，均为 10 万单元格）显示内存随列数而非仅随单元格数增长；
   **分配点未定位**，不声称已优化。
9. **顺序 `page_token`**：协议没有随机定位，只能向前推进，要看第 N 行必须加载前 N-1 行；
   「跳到末尾」必然占用与已加载行数成正比的内存。
10. **只有 debug 构建的基准**：冷启动与内存数值全部来自 debug 构建，release 构建未测量。
11. **TLS 未做真实握手验证**：5 档模式映射与参数校验有单元测试；测试容器未启用 TLS，
    `require` / `verify-ca` / `verify-full` 与客户端证书**未验证**；MySQL 8.x 同样未验证。
12. **真实密钥环用例未运行**：`secret_service_semantics` 需 `SQARVO_SECRET_SERVICE_TEST=1`
    且在桌面会话下运行，本次发布验证未设置该变量；Windows Credential Manager 与
    macOS Keychain 未实现，装配为「不可用」。
13. **大字段只能标记截断**：不提供延迟加载或完整值回取；单元格的 `original_type_name`
    后端 `mapping.rs` 尚未填充（只有列元数据带原始类型名）。
14. **类型语义的已知边界**：MariaDB `TIMESTAMP` 按服务端返回的墙上时间交付、不做时区换算；
    `JSON` 是 longtext 别名，按文本展示；数组类型未支持（仅 PostgreSQL 有）。
15. **无复制/导出**：`REQ-RESULT-003` 未实现，结果区没有复制或 CSV/JSON/SQL 导出入口。
16. **版本号未提升**：后端 workspace 版本仍是 `0.1.0`，端点文件与 `GetVersion` 的
    `service_version` 仍为 `0.1.0`——不要用它判断是否 v0.2。
17. **配置文件损坏时没有备份**：`connections.json` 无法解析时，前端打印警告并按空连接列表
    继续运行（读取路径不写盘）；用户随后保存连接会通过 `write_atomic` 的 rename 覆盖该文件，
    损坏内容不保留副本，原本记录的其他连接会从列表中消失。

## 升级注意

- **`credential_ref` 格式**：固定前缀 `sqarvo:conn/` + 小写、带连字符的 UUID v4，
  例如 `sqarvo:conn/3f9a1c4e-7b2d-4a6f-9c11-0d2b8e5a71f4`（ADR 0012）。
  引用里禁止编码主机、用户名或库名；格式非法 → `INVALID_ARGUMENT` + `config.invalid`；
  格式合法但凭据不存在 → `NOT_FOUND` + `credential.not_found`，且**不会尝试连接数据库**。
  删除凭据不会删除配置文件里的引用，之后连接会得到 `credential.not_found`。
- **`protocol_version` 仍为 `v1`**：后端常量与 Linux 客户端常量都是 `v1`，端点文件与
  `SystemService.GetVersion` 也返回 `v1`。因此按 v0.1 契约实现的客户端**不会**因版本被拒绝。
  但这类客户端不认识 `CredentialService`，也就拿不到 MariaDB 密码：连接会在认证阶段失败
  （`mariadb.auth_failed`），而不会退回「密码作为连接参数明文传递」的旧路径
  （该路径从未存在）。
- **端点文件字段不变**：`transport` / `socket_path` / `host` / `port` / `token` / `pid` /
  `protocol_version` / `service_version`；路径仍是
  `$XDG_RUNTIME_DIR/sqarvo/backend-endpoint.json`，权限 0600。端点文件变化只随 token 与
  socket 路径变化，升级无需手工清理——前端会校验 `pid` 是否存活并把陈旧端点视为需要重启后端。
- **新增服务不影响旧客户端**：proto3 客户端忽略未知服务与未知字段，既有
  `ConnectionService` / `QueryService` / `SystemService` 的消息字段号未变、未复用、未删除。
- **配置迁移**：v0.1 没有可配置的前端，因此没有迁移动作；Linux 前端首次保存连接时会创建
  `connections.json`（`DOCUMENT_VERSION = 1`）。配置文件**损坏或不可解析**时，前端打印警告并
  按空连接列表处理（`src/config.rs::load_file`）；此时再保存一条连接会用新内容覆盖该文件，
  损坏的旧文件不做备份（见「已知限制」17）。
- **结果集上限**：默认 500000 行 / 512 MiB；列很多的库建议显式调低
  `SQARVO_RESULT_BYTES_LIMIT`（宽表实际内存远高于估算，见「已知限制」7、8）。
- **版本号**：`service_version` 仍是 `0.1.0`，请用本文与支持矩阵判断能力，而不是版本字符串。

### 结论

- 冷启动 **240 ms**（debug），空闲 **149.3 MB**，10 万行 **2.8 s / 191.6 MB**：
  达到 v0.2「10 万行场景可用（有基准记录）」的退出标准，数值可复现；
- 背压有效：10 万行查询在**不滚动**时 3 秒后仍只有首批 500 行、没有后续批次，
  日志记录「暂停预取：未滚动到新区域所以不预取」；
- 结果集上限有效：`SQARVO_RESULT_ROW_LIMIT=1000` 时在 1000 行处停止拉取，界面显示
  `result.limit_reached`，已加载数据保留，随后执行新查询正常返回；
- **未达到/未验证**：
  - 200 列 × 2000 行占 **603.4 MB**，明显高于按行数的直觉预期。同一轮对照实验：
    20 列 × 5000 行 208.6 MB、100 列 × 1000 行 376.5 MB（三者都是 10 万单元格），
    说明内存随**列数**上升而非仅随单元格数；200 列 500 行 563.5 MB → 2000 行 603.4 MB，
    行数增加只多 40 MB。**具体分配点未定位**，不声称已优化；
  - 冷启动与内存数值均来自 debug 构建，**release 构建未测量**；
  - 冷启动计时起点是进程内 `main` 入口，exec 后动态链接的几毫秒未计入。

## 性能相关已知限制

- **客户端结果集上限是近似估算**（`result.limit_reached`，默认 500000 行 / 512 MiB）：
  按「行固定开销 + 每格固定开销 + 显示文本 + tooltip」计算，只覆盖前端持有的显示数据，
  **不含 GTK 渲染开销**。实测偏差：10 万行估算 25.3 MiB / RSS 增量约 42 MB（约 1.7 倍）；
  200 列 2000 行估算 40.0 MiB / 实际 603 MB。因此上限是「防止无限增长」的护栏，
  不是 RSS 的精确预测；
- 上限是**客户端**限制，不是服务端错误：与 `query.limit_reached`（服务端并发查询上限）
  语义不同，两者不会混用；服务端没有拒绝任何请求；
- 触顶时**当前批次里放不下的行会被丢弃**（保留已加载前缀并释放游标），调大上限后需要
  重新执行才能拿到完整结果；
- **顺序分页**：协议没有随机定位，`page_token` 只能向前推进；要看第 N 行必须加载前
  N-1 行，因此「跳到末尾」必然占用与已加载行数成正比的内存。服务端可寻址分页/视窗查询
  未实现；
- **宽表内存随列数上升**（约 2 MB/列量级，见上表），200 列场景的实际内存不受估算字节
  上限的良好约束；在列数很多的库上使用时应显式调低 `SQARVO_RESULT_BYTES_LIMIT`；
- 预取有消费门：用户**停在末尾不动**时不会继续拉取，必须继续向下滚动才加载下一批
  （这是背压的代价，换来「不会因为停在末尾就把整表读进内存」）；
- 基准脚本只覆盖单个 Linux 桌面会话下的场景，不包含并发查询、TLS、远程后端或
  HiDPI 下的渲染开销。
