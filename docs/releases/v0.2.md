### 命令

```bash
cd frontend/linux
cargo build
cd ../.. && cargo build -p sqarvo-backend-service
cd frontend/linux && ./scripts/bench.sh --out /tmp/bench.md
```

- 脚本自己清理残留进程（`pkill -x sqarvo-desktop` / `pkill -x sqarvo-backend`）与
  `$XDG_RUNTIME_DIR/sqarvo`，可重复执行；
- 冷启动重复 3 次取**中位数**（不是最好值），样本一并写入输出；
- 任一步失败即非 0 退出并指出步骤；失败时保留日志目录便于复查；
- 输出为 Markdown 表 + `BENCH key=value` 机器可读记录，同时打印到 stdout 并写入文件。

```sql
-- 10 万行
```

### 结论

- 冷启动 **240 ms**（debug），空闲 **149.3 MB**，10 万行 **2.8 s / 191.6 MB**：
  达到 v0.2「10 万行场景可用（有基准记录）」的退出标准，数值可复现；
- 背压有效：10 万行查询在**不滚动**时 3 秒后仍只有首批 500 行、没有后续批次，
  日志记录「暂停预取：未滚动到新区域所以不预取」；
- 结果集上限有效：`SQARVO_RESULT_ROW_LIMIT=1000` 时在 1000 行处停止拉取，界面显示
  `result.limit_reached`，已加载数据保留，随后执行新查询正常返回；
- **未达到/未验证**：
  - 200 列 × 2000 行占 **603.4 MB**，明显高于按行数的直觉预期。同一轮对照实验：
    20 列 × 5000 行 208.6 MB、100 列 × 1000 行 376.5 MB（三者都是 10 万单元格），
    说明内存随**列数**上升而非仅随单元格数；200 列 500 行 563.5 MB → 2000 行 603.4 MB，
    行数增加只多 40 MB。**具体分配点未定位**，不声称已优化；
  - 冷启动与内存数值均来自 debug 构建，**release 构建未测量**；
  - 冷启动计时起点是进程内 `main` 入口，exec 后动态链接的几毫秒未计入。

## 性能相关已知限制

- **客户端结果集上限是近似估算**（`result.limit_reached`，默认 500000 行 / 512 MiB）：
  按「行固定开销 + 每格固定开销 + 显示文本 + tooltip」计算，只覆盖前端持有的显示数据，
  **不含 GTK 渲染开销**。实测偏差：10 万行估算 25.3 MiB / RSS 增量约 42 MB（约 1.7 倍）；
  200 列 2000 行估算 40.0 MiB / 实际 603 MB。因此上限是「防止无限增长」的护栏，
  不是 RSS 的精确预测；
- 上限是**客户端**限制，不是服务端错误：与 `query.limit_reached`（服务端并发查询上限）
  语义不同，两者不会混用；服务端没有拒绝任何请求；
- 触顶时**当前批次里放不下的行会被丢弃**（保留已加载前缀并释放游标），调大上限后需要
  重新执行才能拿到完整结果；
- **顺序分页**：协议没有随机定位，`page_token` 只能向前推进；要看第 N 行必须加载前
  N-1 行，因此「跳到末尾」必然占用与已加载行数成正比的内存。服务端可寻址分页/视窗查询
  未实现；
- **宽表内存随列数上升**（约 2 MB/列量级，见上表），200 列场景的实际内存不受估算字节
  上限的良好约束；在列数很多的库上使用时应显式调低 `SQARVO_RESULT_BYTES_LIMIT`；
- 预取有消费门：用户**停在末尾不动**时不会继续拉取，必须继续向下滚动才加载下一批
  （这是背压的代价，换来「不会因为停在末尾就把整表读进内存」）；
- 基准脚本只覆盖单个 Linux 桌面会话下的场景，不包含并发查询、TLS、远程后端或
  HiDPI 下的渲染开销。
