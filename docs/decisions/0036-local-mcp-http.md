# ADR 0036：本地 MCP Streamable HTTP 与独立服务管理

状态：已接受（维护者确认 #1）

现有 stdio 模式由 MCP 客户端启动。桌面应用需要一种可用稳定本地 URL 接入、可观测且可撤销的服务模式。数据库能力已经由独立 MCP 进程提供。

## 备选

1. 继续只交付 stdio。凭据和进程所有权简单，但没有本地 URL 或桌面端启停控制。
2. 在 gRPC 后端内直接提供 MCP HTTP。少一个子进程，但会把 MCP SDK、HTTP 监听和数据库客户端生命周期合到同一进程。
3. 复用独立 MCP 可执行文件，使用 SDK 官方 HTTP 传输，并由伴生后端监督。保留既有的隔离和 stdio 用法，只为管理增加 RPC。

## 决定

采用方案 3。首版固定 IPv4 回环和 `/mcp`，默认端口 8765，显式启停。手动服务与 GUI 管理的服务独立。后端通过子进程管道确认就绪，以持有的进程句柄和控制管道关闭。父进程丢失时控制管道 EOF，子进程从同一关停路径回收自身。GTK 通过本地认证 gRPC 回读配置和状态。

`rmcp` 3.10.0 负责协议版本、会话和流。HTTP 层认证所有请求，使用准确 Host 和 Origin 匹配，限制请求体、并发认证和会话数量。Linux Secret Service 使用独立的 `mcp-http` profile。Bearer 凭据和数据库访问策略拥有单独的生命周期。关闭全局访问后，新数据库请求立即被现有授权层拒绝。新的 HTTP 配置不进入连接档案。

Codex 客户端配置只引用局部环境变量，用户启动时由 `sqarvo-mcp` 检查同端口的用户私有运行锁，从密钥环读取凭据并传给 Codex。客户端进程及其子进程属于同一用户的信任边界。只有接受安全凭据引用的客户端才适用 HTTP 配置路径，stdio 继续面向无需 HTTP 的客户端。

同版本 MCP 进程通过独立且稳定的审计锁保护整个轮转窗口。审计文件锁继续用于兼容和争用回退。与旧版本进程混跑时，旧进程的轮转仍有 ADR 0032 记录的限制。

## 验证和重新评估

阶段 A 使用 Inspector 2.16.0 验证 `2025-11-25` 与 `2026-07-28`，使用 Codex 0.170.0 验证 `2025-06-18`。本机试验还核对未认证、错误 Host/Origin、版本头、会话隔离及退出。正式验收使用隔离的 GTK、Secret Service 和 SQLite。Codex 0.170.0 经实际密钥环启动器认证，发现 8 个工具，并通过 App Server 的 MCP 调用读取隔离 SQLite。GTK 撤销授权后，相同 HTTP 进程拒绝下一次数据库请求。GTK 正常清理时关闭活动 SSE 并释放托管端口，独立 CLI 服务继续运行。

新增不同平台的 HTTP 认证方式、IPv6、TLS、远程网络访问或其他启动生命周期时，重新评估本记录。
