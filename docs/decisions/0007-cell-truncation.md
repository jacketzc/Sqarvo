# ADR 0007：单元格截断与大字段策略

- 状态：已接受
- 日期：2026-11-04
- 关联：Issue #1、#6；需求 REQ-RESULT-004

## 背景

单行可能包含数 MB 的 TEXT/BLOB。若原样放入批次，会放大 gRPC 消息、内存与前端渲染成本；
若静默截断，用户会误以为数据完整。

## 备选方案

1. **不截断**：数据完整，但一个大字段即可拖垮批次与 UI。
2. **只限制整批字节数**：能控制消息大小，但无法解释「为什么这格是空的/短的」。
3. **每格上限 + 显式截断标记 + 后续延迟加载**：批次可控，且用户知情。

## 决策

采用方案 3：

- 单格文本/二进制上限 `DEFAULT_MAX_CELL_BYTES = 64 KiB`；
- 超限时只发送前缀，并在 `Cell.truncated` / proto `ColumnValue.truncated` 置 `true`；
- 文本截断必须落在 UTF-8 字符边界，不得产生非法编码；
- 截断不改变类型（仍是 TEXT/BLOB）并保留原始类型名；
- 数组元素与「不支持类型」的文本表示同样受上限约束；
- 前端必须把 `truncated` 呈现为可见状态（例如标记 + 「查看完整值」），不得静默；
- 完整值读取（按行/列延迟加载）在后续版本实现；在此之前导出大字段必须明确限制；
- 上限是常量而非配置项，调整需附测量数据（批次大小、内存、渲染耗时）。

## 取舍

- 用户无法在网格中直接看到完整值，需要后续的延迟加载能力；
- 64 KiB 对多数文本足够，但对日志/JSON 大字段会截断；
- 上限集中在一处，便于未来改为按类型或按批配置。

## 重新评估条件

- 实测显示 64 KiB 导致常见字段被截断（需统计真实数据类型分布）；
- gRPC 消息上限或前端渲染能力变化；
- 延迟加载实现后，可下调默认上限。
