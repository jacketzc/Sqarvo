# ADR 0026：界面密度缩放、窗口尺寸与共享度量真值

- 状态：已接受（2026-11-10 评审通过）
- 日期：2026-11-10
- 关联：#158 #159 #160 #161（Linux 前端）、#162 #163（Windows 前端）；AGENTS.md §8（原生前端）、§14.2（UI 口径成对更新）
- 上游：[scaling-and-window-sizing.md](../ui-specification/scaling-and-window-sizing.md)、
  [metrics.toml](../ui-specification/metrics.toml)、[workspace-model.md](../ui-specification/workspace-model.md)

## 背景

用户提出三件事：界面能做 80% / 125% 这类缩放；启动时按显示器选初始窗口大小；以及 Windows 端
开工时要用原生方式支持同一批特性（含暗色）。

调研（`/home/jack/tmp/sqarvo-layout-scaling-darkmode-report.md`，基于 `36ca71e`；本 ADR 的事实
已在 `80aeef6` 上复核并修正）得到三条会改变结论的发现：

1. **向下缩放没有空间**。100% 档已经贴在下限上：`row_height_tree = min_target = icon_button_height = 24`
   （`frontend/linux/src/layout.rs:90,119,133`），`font_data_cell = 13` 且注释写明 12px 渲染 CJK
   会裁笔画（`layout.rs:106-109`）。80% 会得到 19px 命中区与 10.4px 单元格字，同时违反
   `workspace-model.md` §11、`design-principles.md` 的图标描边下限、`layout.rs` 的编译期断言与单测。
2. **向上缩放会把表格吃掉**。窗口固定 1200×800 只放大界面：侧栏 237→356、面板 280→420，
   150% 时只剩 378px 给表格（≈1.26 列，100% 时是 3.26 列）。缩放不能是独立偏好。
3. **最小窗口在高缩放下比屏幕还高**。960×640 在 1080p@200%（逻辑 960×540）与 1366×768@125%
   （逻辑 1092×614）上放不下，底部状态栏永远看不到。这是**现在就坏**的独立缺陷，与缩放无关。

另外复核到两处与会话记录不一致的现状：暗色**已经**跟随系统并有两套品牌色板
（`theme.rs:87-109` 的 `AdwStyleManager::is_dark()` + `connect_dark_notify` + `LIGHT_PALETTE` /
`DARK_PALETTE`），不是「零命中」；硬编码 `set_margin_*` 现为 138 处、`Box::new(orient, N>0)` 54 处。

## 备选方案

1. **连续缩放（0.8–2.0 滑块）**：像浏览器那样任意倍率。三端都要把「基准 × 倍率」算成整数像素，
   而 Rust / C# / Swift 的取整规则不同（half-away-from-zero vs half-to-even），会静默差 1px；
   且连续倍率下每个值都要实测验证，验收成本随档位数量线性上升。
2. **交给系统缩放（GTK `GDK_SCALE` / Windows 显示缩放 / macOS）**：零代码，只能整数倍，
   且**管不了「窗口放不放得下」**——窗口逻辑尺寸不变、物理尺寸加倍，在 1080p 上直接超出屏幕。
3. **只放大字体（`gtk-xft-dpi` / 系统大字）**：只改字号不改 `min-height`，24px 行里塞 16px 字会裁 CJK；
   项目已经踩过这个坑。
4. **三档密度 + 按显示器定窗口 + 共享度量真值**（本 ADR 采用）。
5. **三端各写一套常量**：短期最省，但 Windows 一开写就会出现第二、第三份数字，且没人能证明它们一致。

## 决策

1. **只做三档：`compact` 100% / `comfortable` 125% / `large` 150%，一次到位**，不做连续缩放，
   也不做小于 100% 的档位。
   理由：三档是验收可穷举的数量（3 × {浅色, 暗色, 高对比} = 9 张截图）；向下会破下限（背景 §1）；
   `large` 与 `comfortable` 的工作量同档（都要改同一批代码），分批做只是把重构成两遍。
   「屏幕太小装不下」这个真实诉求交给决策 4 的窗口分档解决，不靠缩到 80%。
2. **缩放的三个轴分开**：系统 DPI 不进应用代码（GTK 逻辑像素 / XAML DIP 已经是密度无关的）；
   界面密度档是应用自己的旋钮；字号跟随系统且不自建第二个设置。
   理由：合成一个数字后，用户永远会遇到「字够大了但行太高」或「行高低了字太小」，
   而两个来源（系统 + 应用）叠加会让「到底是谁在放大」无法解释。
3. **度量真值抽一份 `docs/ui-specification/metrics.toml`，三端只读不计算**（Linux 运行时解析、
   Windows/macOS 构建期生成）。三档的每个值都写成整数，不在各端做 `基准 × scale`。
   理由：跨语言取整规则不同（见备选方案 1），而 1px 偏差只在特定档位出现、肉眼发现不了。
4. **初始窗口按「逻辑工作区分四档」取，不按分辨率**；最小窗口改为 `min(960·T, W-32) × min(640·T, H-48)`。
   理由：4K@200% 的逻辑工作区 = 1080p@100%，按分辨率分档会得出自相矛盾的结论；
   最小窗口不收敛会让 HiDPI 用户拿不到底部状态栏。
5. **Windows 跟随系统标准密度，不复刻 Linux 的紧凑档**；密度档切换在 Windows 上走「重建页面」，
   不追求即时热切。颜色一律 `ThemeResource`，主题走启动期 `Application.RequestedTheme` +
   运行期元素级 `RequestedTheme`，标题栏单独处理。
   理由：ADR 0023 已定「区域一致、控件原生」，密度不属于必须一致的层次；WinUI 的
   `StaticResource` 只解析一次、`ThemeResource` 只在主题切换时重算，热切不可行（除非所有尺寸都
   `x:Bind`，代价是把 XAML 全线绑退化）。重建页面顺带逼出「工作区状态可从模型重建」的能力，
   而多窗口与会话恢复本来就需要它。

## 现在就要守住的接口（后期成本极高）

下面这些不进本轮 Issue，但**新代码从今天起必须守住**，否则以后是一次重写而不是一次改动：

| 项 | 现在做 | 以后做 |
|---|---|---|
| 字符串目录 | 新增 UI 字符串走 crate 内 catalog（只有一个中文 locale 也行），不写字面量 | 44000 行里内联中文，加 gettext 是机械但巨大的改动；德语/俄语长 30%，会撑破 12px 紧凑密度 |
| 无障碍名称与焦点顺序 | 每个可交互控件有 accessible name，Tab 顺序有测试 | 改焦点顺序等于重构控件树；`GtkColumnView` 的单元格语义要逐个补 |
| 动作注册表 | 一张 action 表（id / 名称 / 快捷键 / 可用性谓词 / 平台映射），菜单、快捷键、契约 §8.1 都从它生成 | 现在 15 处 accelerator 分散在控件上、菜单手写、契约另写，三份真相 |
| 列布局持久化 | key 用 (连接, catalog, schema, table) 四元组，宽度按档位归一化 | 存错粒度会复现 #155 那种「跨屏幕串状态」，而且极难发现 |
| 编辑模型 | 现在明确「不做 undo，只有按行回滚」 | 撤销栈要接进编辑状态机，等于重写 |
| 多窗口归属 | 现在定义「会话属于哪个窗口」 | ADR 0023 说 v0.2.3 不做多窗口，但归属模型不定，以后拆窗口要动会话生命周期 |
| 数字排版 | 数字列 `tabular-nums`，等宽字体取系统偏好 | 字体规则散进多份 CSS 后是全局搜替换 |
| 大字段 | 单元格只拿前缀 + 长度，展开再分块取 | 渲染器按整值写，以后改是重写渲染器 |
| 颜色 | 界面 CSS / XAML 里不出现 `#RRGGBB`（例外只有品牌色板：Linux 的 `LIGHT_PALETTE` / `DARK_PALETTE` 与 Windows `Tokens.xaml` 的 `SqarvoBrand*`，两处逐值一致；高对比走系统色） | 品牌色不是系统 token，只能显式登记；散写则会放弃高对比 |

## 取舍

- **三档而不是连续**：用户拿不到 110% 这种「刚刚好」，换来的是可穷举的验收与三端一致的数字。
- **共享 TOML 带来构建期耦合**：改了 `metrics.toml` 就要重生成 C#/Swift 代码，漏了会让构建红
  （这是刻意的——比静默漂移好），代价是三端不能各自独立发版。
- **Windows 密度与 Linux 不同**：跨平台切换时同一屏可见行数不同，「一屏看多少行」不能写进需求
  （ADR 0023 的同类取舍）。
- **切档在 Windows 上要重建页面**：会丢「不进入模型」的临时 UI 状态（比如未提交的输入焦点），
  这是为了不把 XAML 全线绑退化而接受的代价。
- **最小窗口变小**：`min(960·T, W-32)` 在极小屏上会让窗口小于 960×640，紧凑密度在这一档没有保证——
  这是「宁可挤也不要超出屏幕」的明确选择。
- **本 ADR 未做的**：字号档（C 轴）只有跟随系统，没有应用内设置；macOS 的取值列属未验证口径。

## 重新评估条件

- 出现「必须支持 80%」的产品需求：先评估把基准字号抬上去（12→14、13→15）的视觉重构，
  不要直接加档位；
- 出现第四档（如 175% / 200%）的诉求：先确认 `metrics.toml` 的加档流程与不变量测试能覆盖，
  再确认 `--qa-layout-audit` 的档位矩阵成本（每档 ×3 主题）；
- WinUI 出现运行时可重算的资源机制（或 `x:Bind` 全量化的成本被证明可接受）：Windows 的
  「重建页面」策略可以改成热切；
- 顶层要求「三端共享同一份 UI 代码」：与 AGENTS.md §8 冲突，需先改 AGENTS。
