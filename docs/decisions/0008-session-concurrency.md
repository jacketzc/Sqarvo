# ADR 0008：每会话并发与取消

- 状态：已接受
- 日期：2026-11-04
- 关联：Issue #1、#5；风险 R-04

## 背景

`DriverSession` 使用 `&self`，驱动可能内部可变。若允许同一会话并发执行多条 SQL：

- SQLite 单连接无法并行；
- 事务语义会被并发语句破坏；
- 驱动实现必须自行加锁，容易出现锁顺序问题。

另一方面，取消必须能在执行进行中生效，不能排在执行之后。

## 备选方案

1. **允许并发**：吞吐高，但驱动复杂、事务与取消语义混乱。
2. **每会话单条在途语句，取消旁路**：串行化执行，取消直接调用驱动取消句柄。
3. **每会话连接池**：并发能力强，但事务绑定连接、SQLite 不适用，第一阶段过重。

## 决策

采用方案 2：

- `SessionManager` 为每个会话维护异步执行锁（`tokio::sync::Mutex<()>`）；
- `SessionHandle::execute` / `fetch` 持有锁直到驱动返回；锁不得跨无关 `.await`；
- `cancel` **不获取**执行锁，直接调用驱动的取消接口（SQLite：`InterruptHandle`）；
- 同一会话的元数据查询也走该锁（同一物理连接）；
- 查询并发上限由 `QueryRegistry` 在全局层面控制；
- 需要并行的用户应打开多个连接（这是数据库客户端的常规做法）。

## 取舍

- 一条慢查询会阻塞同会话的后续操作，包括取消之外的一切请求；
- 但取消可用、事务边界清晰、驱动实现简单；
- 若未来需要「后台查询 + 继续编辑」，需要重新设计会话模型（多连接或只读副本）。

## 现状（#69 之后）

同一会话的全部**驱动语句**都经 `SessionHandle` 的执行锁串行执行，没有例外路径：

| 路径 | 入口 | 持锁 |
|---|---|---|
| 执行 SQL / 拉取结果 | `execute` / `fetch` | 是 |
| 显式事务 | `begin_transaction` / `commit_transaction` / `rollback_transaction` | 是 |
| 行变更批次 | `apply_row_changes`（#61：校验 + 写入同一把锁） | 是 |
| 浏览一页 | `browse`（`BrowseTable`，#69） | 是 |
| 元数据查询 | `list_children` / `list_children_filtered` / `columns` / `primary_key` / `ddl`（`ListNodes` / `GetColumns` / `GetPrimaryKey` / `GetDdl`，#69、#82、#83） | 是 |
| 行编辑的主键查询 | `ApplyRowChanges` 内的 `table_primary_key`（表数据能力，#69） | 是 |
| 取消查询 | `cancel` | 否——必须在执行进行中生效，故意旁路 |
| 取消行变更批次 | `CancelRowChanges`（#70，ADR 0018） | 否——只置位驱动在行间读取的取消令牌 |
| 释放游标 / 关闭会话 | `close_query` / `close` | 否——生命周期路径，不下发语句 |

实现仍是**单一把 `tokio::sync::Mutex`（互斥锁），不是读写锁**。

两条旁路（`cancel`、`CancelRowChanges`）都不取这把锁，也不 acquire 会话：前者调驱动中断句柄，
后者只做一次原子写。行变更批次的取消因此能在批次**进行中**生效——若它去取执行锁，取消会排在
批次后面等到整批跑完（ADR 0018）。

### 占锁时长实测（#69）

debug 构建、10 万行表、每页 500 行；直接对驱动调用 `browse` 计时——该区间与
`SessionHandle::browse` 的持锁区间一致（锁只覆盖「取能力 + 驱动调用」，结果映射在锁外）。
每档取连续 4 页：

| 驱动 | 数据形状 | 一页耗时（min–max，中位） |
|---|---|---|
| SQLite | 2 列（`id` + 短文本） | 0.48–0.94 ms，中位 0.52 ms |
| SQLite | 9 列 × 180 字符（宽行） | 2.04–3.48 ms，中位 2.68 ms |
| MariaDB | 2 列 | 2.42–4.54 ms，中位 2.69 ms |

同一轮测量里的元数据查询：SQLite `columns` 62–89 µs、`primary_key` 约 61 µs；
MariaDB `columns` 0.58–0.81 ms、`primary_key` 0.41–0.60 ms。

结论：单次占锁远低于 50 ms 的可接受阈值（最坏 4.5 ms，宽行 SQLite 3.5 ms）。
同会话的写批次最多排队一次浏览的时长，用户不可感知；因此**维持互斥锁**，
不为浏览/元数据引入读写锁。

### 为什么读写锁换不到收益

- 浏览与元数据是**同一条物理连接**上的语句。SQLite 单连接、MariaDB 单连接协议
  在驱动内部本来就把命令串成一条序列；「读读并发」在锁层面放行，到驱动仍然排队，
  换不到真实吞吐，只省掉两次浏览之间的一次排队（≤ 数毫秒）。
- 收益是毫秒级排队，代价是写饥饿/公平性：`tokio::sync::RwLock` 写优先，一次长浏览
  （宽表、大二进制列）会把写批次推后，且 `ApplyRowChanges` 会在「主键查询」与
  「写批次」之间两次取锁——读锁放行时这两步之间的窗口会变宽，反而需要额外论证。
- 因此本 Issue 只在 ADR 记下量化结果；若将来单页占锁进入百毫秒级（例如整页 1 MB
  二进制列），按「重新评估条件」先量化再改锁类型。

### 队列语义

同一会话的请求按到达顺序排队（互斥锁先进先出），写操作不会被读操作饿死；
跨会话完全并行，用户需要并行应开多个连接。

## 重新评估条件

- 用户场景要求同会话并行（例如边跑报表边改数据）；
- 驱动支持多路复用协议（PostgreSQL pipeline），可放宽为按连接串行；
- 取消在某些驱动上无法旁路，需要引入优先级通道；
- 单页浏览的占锁时长进入百毫秒级（当前实测 ≤ 4.5 ms），届时考虑读写锁或分页拆分。
