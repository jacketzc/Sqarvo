# ADR 0004：规划文档与任务跟踪的分工

- 状态：已接受
- 日期：2026-11-04

## 背景

项目包含三个原生前端、统一 Rust 后端、Driver SPI、gRPC 契约与多个数据库驱动，
周期长，且未来会有其他开发者与多个 AI Agent 参与。需要明确：

- 哪些内容必须随代码一起版本化；
- 哪些内容属于高频变化的执行状态；
- 多个 Agent 如何避免各自修改规划导致不一致。

## 备选方案

1. **全部放在仓库**：计划、任务清单、进度都用 Markdown 维护。
   优点是单一来源；缺点是任务状态与代码评审脱节，Issue/PR 信息无法联动，
   多人/多 Agent 同时改同一文件冲突频繁。
2. **全部放在外部工具**（Notion / Jira / 在线文档）：仓库只放代码。
   缺点是规划与代码不同步，贡献者需要额外权限，开源协作门槛高。
3. **分层**：仓库保存长期规划与决策，GitHub Issues/Projects 保存任务与进度。

## 决策

采用方案 3：

- `docs/product/`：愿景、定位、需求、路线图（低频、需评审）；
- `docs/planning/`：实施计划、里程碑、发布计划、风险（中频、由项目管理角色维护）；
- `docs/architecture/`、`docs/api/`、`docs/database/`、`docs/ui-specification/`、`docs/decisions/`：
  技术与设计事实（随代码变更同步更新）；
- GitHub Issues：可独立执行、可验收的具体任务；
- GitHub Projects：状态流转、依赖与里程碑视图；
- 仓库内不维护第二份任务清单，外部工具不维护第二份规划。

角色分工见 `docs/planning/README.md`：产品规划、项目管理、开发执行三层，
开发 Agent 只更新 Issue/PR，不擅自修改规划文档与里程碑。

## 理由

- 规划需要代码评审与历史追溯，放在仓库可以利用 PR、diff 与 ADR；
- 任务状态变化频繁且需要看板/依赖视图，用 Issues/Projects 成本更低；
- 分层后每个角色有明确写入边界，减少多 Agent 并发修改同一文件的冲突；
- 开源贡献者无需访问外部工具即可理解项目方向。

## 取舍

- 需要在 Issue 与规划文档之间建立链接（Issue 必须写里程碑与需求 ID），否则仍会脱节；
- 仓库与 GitHub 两处都需要维护，但职责不同，不构成重复；
- 依赖 GitHub 平台；若未来迁移，需要导出 Issues 并保留里程碑映射。

## 重新评估条件

- 贡献者主要不使用 GitHub；
- Issues/Projects 无法满足依赖管理或权限要求；
- 规划文档变更频率高到需要独立评审流程。
