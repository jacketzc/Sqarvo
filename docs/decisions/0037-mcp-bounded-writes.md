# ADR 0037：MCP 结构化写入与 MariaDB 部署边界

- 状态：已接受（确认单 #2，MariaDB 部署边界经维护者后续确认）
- 关联：[ADR 0008](0008-session-concurrency.md)、[ADR 0017](0017-table-data-and-row-edit.md)、[ADR 0033](0033-sql-parser-readonly-policy.md)、[ADR 0035](0035-shared-connection-profiles.md)

## 背景

MCP 的总开关和只读开关提供请求级授权。数据库驱动返回的直接影响行数可能不包含触发器
或外键带来的修改。MariaDB 中，拥有目标表 DML 权限的账号可能看不到指向目标表的跨库外键。
因此仅凭该账号的元数据查询和受影响行数，无法限制一次操作的全部写入范围。

## 决策

通过结构化工具接收目标、列、类型化值和条件。每个请求独立使用事务，复用驱动的标识符引用、
参数绑定和会话执行权。检查生成 SQL 的单条语句形态，并在提交前重新核对直接影响行数。
现有只读工具继续使用 ADR 0033 的规则。预览提供当时可见的范围，实际执行重新校验。

SQLite 在写事务内检查目标和可能的连带变更。MariaDB 写入部署采用下列边界：

- DBA 在受管理的实例上显式授权目标。由 DBA 维护的元数据视图只向写入账号返回获准目标
  的资格。视图定义者可以读取完整的入站外键元数据。目标表须通过事务引擎、触发器和外键
  安全检查。缺少资格结果、检查错误或发现潜在连带写入即拒绝。
- 从启用写入到全部写入会话退出，DBA 以服务端权限隔离限制能改变目标或添加入站外键的
  身份，覆盖同实例其他库、继承角色和可代理执行的对象。普通业务身份保留所需 DML 权限。
  保有 DDL 能力的管理入口在这段期间停止执行相关变更。DBA 须先关闭写入并排空在途事务，
  再恢复相关管理权限或运行迁移。
- 写入账号无需全局 `PROCESS`、`RELOAD` 或 DDL 权限。MCP 检查本次目标的资格。
  实例级权限隔离和管理员维护顺序由 DBA 保证，单次查询无法证明其他身份的完整授权状态。
- MariaDB 的部署资格默认关闭。即使本地只读开关关闭，未按该边界配置的档案仍拒绝写入。

事务所有者在提交、回滚或确认连接失效后释放执行权。提交应答丢失时保留未知结果并禁止自动
重放。审计意图须先持久化，事务终态单独追加。没有终态的意图需要人工核对。

## 备选与证据

在使用合成数据的 MariaDB 11.8.6 实例上复现：

- 目标表普通 DML 账号看不到跨库级联外键，删除父行后子行仍被删除，直接计数为一。
- `SELECT … FOR UPDATE` 和 `LOCK TABLES … WRITE` 均未阻止使用
  `foreign_key_checks=0` 创建跨库引用。仅检查目标表的锁无法关闭这个竞态。
- `BACKUP STAGE BLOCK_DDL` 可以阻止其他会话的相关 DDL，但持有屏障的同一会话
  执行 DML 返回错误 4145。两条连接不能保证持锁连接与写入连接同时存活。
- 只授予探针账号 DML 权限时，添加外键和创建跨库引用表均返回错误 1142，
  普通 DML 账号仍能读取资格并提交更新。该探针验证直接授权的行为，完整部署仍需
  验证角色、代理执行、维护窗口与端到端撤权。

## 重新评估条件

当 MariaDB 提供可随 DML 事务一起生效、能覆盖入站外键变化的数据库原生保护时，
重新评估是否能移除部署限制。扩大适用版本或允许日常 DDL 并行之前，须重新验证相关竞态。
