# ADR 0024：跨库浏览以 `ObjectRef.catalog` 为准

- 状态：已接受（2026-11-07）
- 相关：ADR 0021（一标签一会话）、ADR 0022（表浏览分页）、`docs/database/mariadb.md`、
  REQ-META-005、REQ-UI-001

## 背景

v0.2.3 的对象树已经能跨库列对象：`ListNodes(CATALOG)` 读 `information_schema.SCHEMATA`，
`ListNodes(CATALOG=库名)` 读该库的 `information_schema.TABLES`，子节点回传的 `ObjectRef`
里 `catalog` 由服务端填满（`metadata.proto:45-51` 明确要求「跨库引用必须显式，服务端不得
隐式切库」）。

但表数据域没有跟上：MariaDB 的 `table_data.rs` 三处（浏览 281、行变更 859、插入 1817）
都先 `current_database(conn)` 取会话默认库，再由 `metadata::object_parts` 校验
`object.catalog == 默认库`，不等就返回 `capability.unsupported`「只支持当前数据库」。
结果是：树里能看到另一个库的表，双击打开却报错。

同时前端 `driver_form.rs:185` 强制「请填写数据库名」，用户无法「连上服务器再浏览所有库」——
这恰是 Navicat/DBeaver 一类客户端的默认姿势。两处限制叠在一起，用户必须**先知道库名才能连**，
连上以后又**只能看那一个库**。

## 备选方案

1. **会话内切换（`USE <库>`）**：前端在打开表前对该标签会话执行 `USE`。改动最小，
   不需要碰驱动。但会话状态变成隐式且随标签漂移：同一标签连续打开两个库的表，状态栏/标签名
   要跟着变；取消、重连、事务边界都可能拿到错误的当前库；且这不是「引用自带上下文」的模型。
2. **给请求加 `catalog` 字段**：以为契约缺字段，实际 `BrowseTableRequest.object` 已经是
   `ObjectRef`，`catalog` 早就在协议里（`metadata.proto:76-82`），缺的只是驱动实现。
3. **以 `ObjectRef.catalog` 为准**（本 ADR 采纳）：驱动按请求里的 `catalog` 取库并拼限定名，
   只有 catalog 缺省时才回落到会话当前库（兼容旧客户端与「根节点」查询）。

## 决定

1. **对象的库归属由请求携带，不由会话决定。** 驱动解析 `object.qualified_name.catalog`：
   - 非空 → 用该库拼限定名，**不**校验它与会话默认库是否一致；
   - 为空 → 回落到会话当前库（既有无 catalog 客户端行为不变）；会话也没有默认库时返回
     `metadata.no_database`（沿用现有错误码 `NO_DATABASE`），文案改为「请在连接里填写默认库，
     或从对象树选择具体库的表」。
2. **绝不隐式切库。** 驱动不执行 `USE`，不改会话状态；一个标签打开 A 库的表、另一个打开 B 库的
   表，两者互不影响。这与 ADR 0021「一标签一会话」天然相容：会话只承载连接与事务，
   库归属跟着引用走。
3. **前端「数据库」可为空。** 连接配置的 `database` 变可选；会话名在无默认库时退化为
   `用户@主机`（不再生成 `user@host/` 这种残缺名字）。树根节点在无默认库时不显示对象，
   而是直接展示库列表（`CATALOG` 层），与有默认库时一致地懒加载。
4. **SQLite 只接受自己的目录名。** `main` / `temp` 之外的 catalog 明确报
   `capability.unsupported`，不再静默按 `main` 处理（当前行为会把「请求了别的库」当成
   「请求了 main」，属于静默降级）。
5. **行变更与插入同样按 catalog 定位。** 写入必须落在用户看到的那个库，不允许
   「树里是 B 库的表，写入打到 A 库」。
6. 不需改 Protobuf：字段本来就有。此决定只改三个驱动的实现与前端表单，**不产生契约增量**，
   旧客户端行为不变（catalog 缺省时语义与 v0.2.3 完全一致）。

## 理由

- 协议早就写下「引用必须显式、服务端不得隐式切库」（`metadata.proto:45-47`），
  表数据域的实现只是漏了这条。修正它不需要新协议，也不需要新依赖。
- 会话内 `USE` 把「我在哪个库」变成隐藏状态：标签名、状态栏、面板、事务、重连都要
  额外同步这份状态，而它随时可能被用户的一条 SQL 改掉——用户执行 `USE other` 之后，
  标签显示的库和实际库就不一致了。引用自带上下文没有这个问题。
- 无默认库也能连，是这类客户端的标准交互；它还把「先连服务器、再挑库」这个常见动作
  从「猜库名」变成「点一下」。

## 代价与取舍

- 驱动每条表数据语句都要带库前缀（`\`db\`.\`table\``）。MariaDB 支持；SQLite 的
  `main`/`temp` 也支持。对 `information_schema` 之类的系统库，读表数据依然允许
  （用户能看到什么由权限决定）。
- 行为变化：以前跨库浏览报 `capability.unsupported`，现在会真的读那个库。
  这对「只读浏览」是严格的能力增强；对**行变更**意味着写入范围变大，
  因此第 5 条要求写入路径同样显式绑定 catalog，并在验收里断言「打开 B 库的表、
  提交一行、A 库不受影响」。
- 默认库仍然有用：它是「没有 catalog 的旧客户端」和「树根节点」的落点。因此连接配置保留
  可选默认库，而不是删掉这个字段。

## 何时重新评估

- 引入 PostgreSQL（有 catalog + schema 两层）时：本决定按 catalog 定位，schema 由
  `object.schema` 携带，规则不变；若发现 schema 缺省语义需要「搜索路径」，
  另立 ADR，不要偷偷用连接默认值。
- 若将来支持「同一标签在多个库间来回切」的显式 UI（例如库下拉框），该状态应由
  **标签**持有并显示，仍然不写进会话；届时应重新审视第 2 条。
