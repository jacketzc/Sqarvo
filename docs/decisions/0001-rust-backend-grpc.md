# ADR 0001：Rust 独立后端 + gRPC

- 状态：已接受
- 日期：2026-11-04

## 背景

需要同时支持 Windows（WinUI 3 / C#）、Linux（GTK4 / Rust）、macOS（SwiftUI / Swift）。
若每个平台各自实现数据库连接、SQL 执行与结果集管理，会带来三份协议实现、三套安全策略
与不可控的行为差异。

## 备选方案

1. **纯原生三份实现**：每端直连数据库。性能最好，但维护成本与安全风险最高。
2. **Web 技术统一实现**（Electron/Tauri WebView）：开发快，但违背「原生、轻量」定位，
   且无法满足启动速度与内存目标。
3. **独立 Rust 后端进程 + gRPC**：数据库逻辑只实现一次，各平台只做 UI。

## 决策

采用方案 3：

- 后端为独立进程 `sqarvo-backend`，Rust + Tokio + tonic；
- 前端通过 gRPC 调用，契约由 `proto/` 生成；
- 前端负责 UI、平台集成与后端生命周期；后端不依赖任何 UI 框架。

## 取舍

- 优点：驱动与安全策略单点实现；前端可替换；便于测试与后续远程化。
- 代价：多一个进程与 IPC 层；需要处理启动顺序、端点发现、崩溃清理；
  跨语言代码生成增加构建复杂度。
- 已缓解：本地 IPC 使用 Unix socket + token（Windows 回退回环 TCP + token）；
  端点文件原子写入；构建脚本内置 protoc，避免环境差异。

## 重新评估条件

- 若 IPC 开销在实测中成为主要瓶颈（需有基准数据）；
- 若 gRPC 在某一平台无法可靠支持安全传输（例如 Named Pipe 长期不可用）；
- 若产品需要远程后端，需重新设计认证与 TLS 模型。
