# ADR 0005：结果集游标由驱动持有

- 状态：已接受
- 日期：2026-11-04
- 关联：Issue #1、#3；风险 R-02

## 背景

查询结果必须分批返回，且分页期间结果集要稳定（不能重复或丢失行）。可选做法直接影响
驱动实现、内存占用与取消语义。

## 备选方案

1. **重新执行 + OFFSET/LIMIT**：每次 fetch 重跑 SQL 并跳过前 N 行。
   - 优点：驱动无需持有状态。
   - 缺点：表在分页期间变化会导致重复/丢失；重跑代价随偏移增长；非确定性查询无法保证。
2. **一次性取全量再切片**：简单，但违反「大结果集不一次性进内存」，不可接受。
3. **驱动持有游标**：执行时建立游标，fetch 只推进游标，token 由服务端签发。
   - 优点：结果稳定、内存受批次上限约束、取消/关闭语义清晰。
   - 缺点：游标与会话绑定，需要生命周期管理与断连清理。

## 决策

采用方案 3。

- `Execute` 返回 `ExecutionStart`（语句摘要 + 首批），后续 `FetchBatch` 携带不透明 token；
- token 由后端生成，绑定 `(query_id, statement_index)` 与会话，客户端不得解析；
- 游标所有权属于驱动；后端只负责登记、限额与在关闭/断连/取消时调用清理；
- 游标在以下情况必须释放：结果读完、`Close`、会话断开、查询超时、进程退出；
- 驱动无法持有游标（例如无状态 HTTP 查询接口）时，必须声明不支持流式结果并返回
  `capability.unsupported`，不得用 OFFSET 伪装。

## 取舍

- 每个活跃查询占用驱动侧资源（SQLite：一个 prepared statement + 连接线程）；
  通过并发上限与批次上限控制。
- 断连清理成为必须实现的路径，不能依赖 GC。
- 前端必须在结果读完或关闭标签时调用 `Close`；后端仍需在断连时兜底。

## 重新评估条件

- 出现无法持有游标但必须支持的数据库接口；
- 实测显示游标长期占用导致连接数或内存不可接受；
- 需要支持跨会话的断点续传（届时需持久化游标，超出本设计）。
