# ADR 0029：UI 验收边界（agent 验交互与功能，样式人工确认）

- 状态：已接受（2026-11-16，维护者指示「修改一下 ui 验收方式（全局）」）
- 日期：2026-11-16
- 关联：AGENTS.md §13（测试要求）、§14.3（组件注册表）、§15.0（改动确认单）、§16（交接模板）；
  `docs/ui-specification/components/README.md`（`sync` 字段口径）
- 上游：[ADR 0023](0023-cross-platform-shell.md) §7（验收按语义不按像素）、
  [ADR 0025](0025-ui-behavior-contract.md)（截图不是规范）

## 背景

项目里已经有两条相邻的原则，但都只覆盖**一部分**场景：

- ADR 0023 §7：「验收按语义不按像素——自动化证据读取控件文本 / 可访问性名称，不比较截图坐标；
  截图只作为目检材料。像素级对齐不作为任何一项验收标准。」这句话约束的是**三端一致性**。
- ADR 0025 的一条取舍：「截图 / 录屏当规范——能证明『长什么样』，证明不了『什么条件下可用、
  失败后去哪』。」这句话约束的是**行为规范**。

但在具体任务里，agent 仍然会把截图当成验收证据：AGENTS.md §15.0 的改动确认单模板里，
「验收」字段明确把「截图」列为可选证据之一；注册表的 `sync.<plat>.evidence` 没有规定证据形态；
`docs/planning/` 下的里程碑与发版记录里大量引用截图文件名。

问题不在于「用了截图」，而在于**agent 拿截图去下样式判断**：

1. **不可复现**。「看起来像文件资源管理器」不是一条能复跑的断言；换台机器、换个缩放、换个
   主题，同一份截图就能得出不同结论。
2. **越权**。样式是审美判断，最终决定权在维护者手里；agent 对「间距是 4 还是 6」「圆角是不是
   12」「颜色对不对」没有可靠的判据，签字等于背书了一个它并不具备依据的结论。
3. **本项目的截图本来就不等于真机**。Windows 端的 `--screenshot` 用 `RenderTargetBitmap`
   只渲染 `Window.Content` 的 XAML 像素，**拍不到 DWM 合成的材质**（Mica / Acrylic）；
   Linux 端是 GTK 自渲染，与真机观感不同；Wayland 下还没有 OS 级截屏与真实指针注入。
   「截图能证明样式」这件事在本项目从来不成立。

维护者的要求：**agent 仅验收 UI 的交互与功能，不做样式验证，不做图像识别；样式由人工确认。**

## 备选方案

1. **全面禁止截图作为证据**（连给人工看的材料也不产出）：不现实。人工目检仍然需要图，
   只是不由 agent 判断。
2. **只改 AGENTS.md §15.0 的模板措辞**：只约束「以后出单时怎么写」，注册表口径与发版门禁口径
   不变，规则会分裂成两套。
3. **写进 AGENTS.md + 组件注册表 README，并用一份 ADR 记录边界**（本 ADR 采用）：工作规则、
   登记口径、决策依据三处对齐。
4. **加一条 CI lint，拒绝 `evidence` 里出现「截图」字样**：收益低、误伤高——历史条目里有描述性
   引用（`data_page.toml` 里有一句「窗口自渲染截图拍不到」是**事实陈述**，不是证据）。暂不做。

## 决策

1. **agent 的 UI 验收范围 = 交互 + 功能。** 可以作为证据的：命令退出码、断言输出、QA 开关打印的
   结构化行、可访问性名称 / 控件文本的读取结果、状态迁移（某控件出现、某属性变更、某回调触发）。
2. **不做样式验证**：不判断颜色、间距、圆角、字号、对齐、密度档的视觉效果。
3. **不做图像识别**：不读截图去推断外观，不做像素比较，不以截图作为「看起来对不对」的依据。
4. **样式由人工确认**：改动确认单的「验收」字段里，样式类条目一律写「人工确认」；agent 在
   报告里**不宣称**样式已验收，只说「已实现，样式待人工确认」。
5. **注册表 `sync.<plat>.evidence` 只写交互 / 功能证据**（命令、断言、QA 开关输出、可访问性名称 /
   控件文本的读取结果）。历史条目里已引用的截图不必回改，但新登记不再以截图为准。
6. **不追溯改写历史记录**：`docs/planning/` 下的里程碑、发版记录、Issue / PR 描述里的截图引用
   保持原样——它们是历史记录，不是当前口径。
7. **截图仍可产出，但只作为人工目检材料**：agent 可以调 `--screenshot` 之类开关把文件交给人看，
   **不得**据此下「样式正确 / 不正确」的结论。

## 理由

- **可复现**：agent 的每条结论都要能从命令与断言里复跑出来。「看着像」复跑不出来。
- **边界清楚**：交互与功能是**可断言**的，样式是**审美**的。把审美判断交回有最终决定权的人，
  是分工，不是推卸。
- **与既有决策同向**：本 ADR 是 ADR 0023 §7 与 ADR 0025 的**全局化**，不是另立一套口径——
  它把「按语义不按像素」从「三端一致性时」扩到「所有 UI 验收」。
- **不制造虚假完成度**：样式改动做完了就是做完了，agent 如实报「样式待人工确认」，比签一个
  自己验不了的字更诚实。

## 代价与边界

- **agent 的完成度看起来会低一档**：样式类改动做完，agent 只能报「已实现，样式待人工确认」，
  不能自己签字。这是有意的。
- **有些现象只能靠看才判断**（例如「这行是不是被裁了」「这个面板是不是叠住了」）：要么转成
  结构化断言（控件几何、可见性、`--qa-layout-audit` 的越限项），要么明确交给人工。
  **不许含糊**——不许写「看起来没问题」当作验收。
- **新旧口径并存**：历史记录里的截图引用不清理，读者可能误以为截图仍是验收标准；靠本 ADR 与
  AGENTS.md §13 指明当前口径。
- **QA 开关不因此失效**：`--qa-*` / `--report-*` 的价值在于它们打印的是**结构化事实**，不是像素。
  它们继续作为 agent 的主要证据来源。

## 复评条件

- 出现**可靠且确定性的**样式校验手段（例如带标注的视觉回归基线 + 确定性渲染，且有可复现的
  渲染环境）：重新评估是否放开「样式验证」这一项。
- 产品要求把「视觉一致性」纳入发版门禁：需要另出一份 ADR 定义门禁口径与豁免办法。
- 人工目检的负担超出可承受范围：重新评估哪些样式项可以下沉为结构化断言。
