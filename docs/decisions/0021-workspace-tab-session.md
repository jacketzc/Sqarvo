# ADR 0021：工作区标签与数据库会话的映射

- 状态：已接受（2026-11-07 评审通过）
- 日期：2026-11-07
- 关联：Issue 待建；REQ-UI-001、REQ-UI-002、REQ-TXN-001；
  ADR 0008（每会话并发与取消）、ADR 0009（SQLite 驱动）、ADR 0011（MariaDB 驱动）、
  ADR 0018（行变更取消）
- 上游：[workspace-model.md](../ui-specification/workspace-model.md)

## 背景

v0.2.3 的工作区要支持多标签：同一连接下可同时打开多个表数据标签与查询标签。现有实现是
「一个窗口 = 一个会话 = 一个页面栈」（`frontend/linux/src/ui.rs` 的 `Workspace` 只持有一个
`session_id`），而 [ADR 0008](0008-session-concurrency.md) 规定同一会话内所有驱动语句串行
执行，取消是唯一旁路。

一旦把多标签做出来，就必须回答四个互相关联的问题：

1. 标签与会话是一对一、一对多还是多对一；
2. 对象树的浏览（展开、搜索、DDL、列信息）走哪个会话；
3. 事务作用域是标签还是连接，用户看到的差异是什么；
4. 关闭标签、断开连接时的资源与回滚语义。

这些问题不能只在前端层解决：它们决定后端会话数量、连接数上限、错误语义与 UI 状态模型。

## 备选方案

1. **单会话多标签共享**：仅在界面层加标签，所有标签共用一个会话。
   改动最小，事务作用域天然清晰；但 ADR 0008 的执行锁会让「标签 A 跑慢查询」直接阻塞
   标签 B 的翻页、树的展开与列信息查询，多标签的主要价值（并行查看）拿不到。
2. **一标签一会话 + 每连接一条浏览会话**：标签各自 `Connect` 出会话，树用连接级常驻会话。
   真正的并行与独立事务；代价是连接数随标签增长、跨标签未提交数据互不可见、
   SQLite 同文件多连接出现写冲突。
3. **每会话连接池**：并发最灵活，但事务绑定连接、SQLite 不适用、资源上限难说清，
   与 ADR 0008 的取舍方向相反，第一阶段过重。

## 决策

采用方案 2。

1. **一标签一会话**：标签创建时 `Connect` 一个新的会话，关闭时 `Disconnect`。标签内的所有
   操作（浏览、编辑、事务、取消）都发往该标签自己的会话。
2. **每连接一条浏览会话**：对象树的展开、对象搜索、`GetColumns`、`GetPrimaryKey`、`GetDdl`
   走连接级常驻会话，与任何标签会话互不影响。它不参与标签事务，也不执行用户 SQL。
   因此连接数 = 1（浏览）+ N（标签）。
3. **事务作用域 = 标签**：`Begin` / `Commit` / `Rollback` 作用于当前标签的会话。界面必须在
   标签上标出事务态（自动提交 / 事务中 / 失败态），并在状态栏显示当前标签会话的事务状态。
   一个标签的未提交更改对其它标签**不可见**（不同会话），这是数据库语义，不是缺陷；
   界面在「同一 catalog 存在其它未提交事务」时给一行提示，避免用户把它当成刷新失效。
4. **并发上限**：客户端标签会话上限默认 8，与 `QueryRegistry` 的 `max_concurrent`
   （`backend/crates/query-engine/src/registry.rs`，默认 8）对齐；超限时拒绝新建标签
   并给出可读原因（含当前上限与关闭建议），不静默失败。上限可配置。
5. **SQLite 的多连接风险如实处理**：驱动每会话独立 `Connection::open_with_flags`，当前没有
   `busy_timeout`，也没有 `journal_mode=WAL`。v0.2.3 在驱动连接建立时设置
   `PRAGMA busy_timeout`（默认 5000 ms，有界等待），把「立即失败」变成「有界等待后失败」。
   **不**自动切换 `journal_mode`：那会持久改变用户数据库文件（生成 `-wal`/`-shm`），
   属于对用户数据的副作用，只能作为显式设置项另议。
   同时明确记录：SQLite 的一标签一会话不带来吞吐收益（同一文件仍串行写入，且每会话是一根
   专用线程），它换来的是事务隔离与界面不互相阻塞。
6. **关闭与断开**：
   - 关闭标签 → `Disconnect` 该标签会话；未提交事务由服务端回滚；有脏行时提供
     保存 / 放弃 / 取消 三选。
   - 断开连接 → 关闭该连接下全部标签与浏览会话，二次确认时必须列出将被关闭的标签名。
   - 后端消失 / 断线 → 所有标签进入 Disconnected，保留已加载行，不回滚界面缓存，
     重连后不自动提交任何东西。
7. **前端事件路由**：后端连接保持单进程、单 channel、多会话；前端 worker 的命令与事件
   必须携带 `tab_id`（或等价的归属标识），主线程按标签路由。禁止用「最近一次请求」推断归属。
8. **浏览会话不参与标签事务**：这保证即使某个标签处于失败态事务，对象树仍可展开、
   DDL 仍可查看。

## 取舍

- 连接数随标签线性增长：MariaDB 每个会话是一根 `Conn`（无池），需把
  `max_connections` 计入使用说明；SQLite 每个会话一根专用线程，内存随标签增长。
- 跨标签数据可见性差异需要文案支撑，否则会被当成 bug。
- 8 个标签的上限是保守值：它同时受 `QueryRegistry` 与数据库端连接数约束，
  真正放宽需要先有「按连接可配置 + 连接数观测」。
- 浏览会话让连接数从 N 变成 N+1；换来树不会被标签事务拖住。
- 一标签一会话暴露了 SQLite 的 `SQLITE_BUSY`，必须靠 `busy_timeout` 兜底；写冲突仍然
  可能发生，错误文案要能指向「另一个标签正在写同一个库」。

## 重新评估条件

- 出现「标签很多但数据库连接数受限」的真实场景（如托管数据库的 20 连接上限）；
- PostgreSQL（M5）驱动引入后，多会话成本或语义出现明显差异；
- 需要「同一标签内并行后台查询」时——这与 ADR 0008 一并重评；
- SQLite 的 `busy_timeout` 在实测中不足以覆盖常见写竞争（需要 WAL 决定）。
